# ADR-017: MaaS Cluster Visibility via Read-Only CustomObjectsApi Reads

## Status

Accepted

## Context

MaaS:PAL only ever showed information about *test runs* — scenarios, tasks, assertions, logs. It had no view of the *MaaS setup being tested*: what subscriptions exist, what quotas/rate limits they carry, which models they cover, and who can reach them. An admin had to `oc get` a handful of CRDs by hand before designing a scenario against a given cluster.

Live exploration of a real RHOAI MaaS install (`kube:admin` on `cluster-rkmhx...`) showed the richest data — `spec.priority`, `spec.owner.{groups,users}`, per-model `tokenRateLimits`, live `status.conditions` (including a `SpecPriorityDuplicate` condition that flags real misconfigurations) — lives only in the `MaaSSubscription`/`MaaSModelRef`/`MaaSAuthPolicy` CRDs, not in the MaaS REST API (`GET /v1/models` returns a much thinner shape: `id`, `url`, `ready`, `subscriptions[]` names only). Reading these CRDs cluster-wide (their namespace, e.g. `models-as-a-service`/`llm`, is install-specific and not fixed) requires RBAC the `maaspal` SA doesn't have today.

See `docs/architecture/maas-domain-reference.md` for the full information catalog this ADR's reads are meant to serve, and ADR-009 for the existing (harness-side, write) use of `MaaSSubscription`.

## Decision

**Read via `kubernetes.client.CustomObjectsApi` from the API server process itself, not the harness Job.** This is standing cluster-state, not something tied to a single run — it belongs in `api/`, polled by the browser, independent of any Job lifecycle. `api/maas_client.py` is a new module, parallel to `api/k8s.py` (which manages Jobs/pods) rather than an extension of it, since the two have no logic in common beyond "call the Kubernetes API."

**Cluster-scoped `ClusterRole`, not a namespaced `Role`.** `deploy/rbac-maas-readonly.yaml` grants `get`/`list`/`watch` on `maassubscriptions`, `maasmodelrefs`, `maasauthpolicies`, `tenants`, `externalmodels` (`maas.opendatahub.io`), `tokenratelimitpolicies` (`kuadrant.io`), `limitadors` (`limitador.kuadrant.io`), `llminferenceservices` (`serving.kserve.io`), `gateways`/`httproutes` (`gateway.networking.k8s.io`), `groups` (`user.openshift.io`), `datascienceclusters` (`datasciencecluster.opendatahub.io`), `odhdashboardconfigs` (`opendatahub.io`), and core `namespaces` — bound cluster-wide via a `ClusterRoleBinding`, the same pattern `deploy/rbac-monitoring.yaml` already uses for `cluster-monitoring-view`. A namespaced `Role` would need to name the MaaS install's namespace explicitly, which isn't fixed across clusters; `Kubernetes serves `list_cluster_custom_object` the same way `kubectl get <plural> -A` does for a namespaced CRD, returning items across every namespace the caller can see, so a single cluster-wide grant covers every install layout without per-namespace configuration. This is read-only introspection of RHOAI's own resources (get/list/watch only, no write verbs) — consistent with the project's existing stance of acting through RHOAI's own resources rather than bypassing its access controls, not a new category of access. `namespaces` (get/list/watch) is the one grant here that isn't a MaaS-specific CRD — it's needed only to read a model's namespace `labels` for the `maas.opendatahub.io/gateway-access` check (see Phase D below).

**Graceful, per-resource degradation — never a hard failure.** Every read in `api/maas_client.py` returns a `ResourceList(available, items, reason)` rather than raising: a `403` (RBAC not applied) or `404` (CRD not installed — e.g. a cluster without MaaS at all, or without the `ExternalModel` tech-preview CRD) both resolve to `available=False` with a `reason`, and the caller renders whatever *is* available. This was an explicit requirement (not everyone deploying MaaS:PAL will have applied `rbac-maas-readonly.yaml`, or will be running a MaaS version with every CRD in this list) — one missing grant must degrade only the section it backs, not the entire "MaaS Setup" view, and must never affect the pre-existing Runs functionality at all. `GET /api/maas/status` exposes this per-section so the frontend can hide/warn rather than render an empty or broken table.

**Models are a merge of three sources, not a single read.** `MaaSModelRef` (CRD — display metadata, endpoint), the MaaS REST `GET /v1/models` (the only place the subscription→model reverse-index is exposed), and `LLMInferenceService` (CRD — replicas/resources/serving readiness, only fetched when a model is internally served) are combined into one shaped record per model in `list_models()`. The REST call is best-effort (`_fetch_v1_models` swallows any failure and returns an empty cross-reference) since it depends on `MAAS_API_URL`/the SA token being usable, separately from whether the CRD reads succeed. Each model also carries an explicit `hosting: "internal" | "external"` field — derived from `modelRef.kind == LLMInferenceService`, not inferred from the absence of other fields — so the UI never has to guess when a future backing kind shows up with `kind` unset. The shaped `namespace` field (already carried since the first version of this endpoint, for API purposes) is surfaced directly under the Hosting badge in `ModelsTab.tsx` — a model's namespace is where the underlying `MaaSModelRef`/`LLMInferenceService`/`ExternalModel` object actually lives, which matters for cross-checking against `oc get` output on a real cluster.

**Access Control is an all-or-nothing comparison between two sources, with a softer third.** `list_access()` (`GET /api/maas/access`) cross-references `MaaSSubscription.spec.owner.groups` (quota) against `MaaSAuthPolicy.spec.subjects.groups` (gateway access) per group, computing `quota_without_access`/`access_without_quota` model-name diffs — the two misconfiguration classes called out in the domain reference (Catalog item C). Unlike every other section here, this one can't degrade to "show what's available": the entire feature *is* the comparison, so if either subscriptions or auth policies is unreadable, the whole section reports unavailable (with that source's own reason) rather than a half-comparison that would misrepresent which model coverage is actually missing. OpenShift `Group` (`user.openshift.io/v1`, cluster-scoped) is treated as strictly softer — its absence still shows group names and the subscription/auth-policy comparison, just with `users: null` (never an empty list, which would incorrectly read as "confirmed no members") instead of resolved usernames.

**Access Control's YAML views are per-object, not per-row.** A group row can reference multiple subscriptions and multiple auth policies, so `list_access()` carries a `raw_yaml` on each subscription/auth-policy reference (reusing `list_subscriptions()`'s own `raw_yaml` for the subscription side, computing a fresh one for auth policies) plus one `raw_yaml` for the group's own `Group` CR (`None` when Groups is unavailable — used by the UI to decide whether to even offer a "View YAML" link for the group, rather than offering a link that would show nothing). In `AccessControlTab.tsx` each subscription/auth-policy chip is independently clickable, opening that specific object — there's no single "the YAML for this row" concept once a row can span several CRs.

**"View YAML" reuses the run-settings viewer, and both must stay lazy-loaded.** `RunSettingsModal`'s read-only Monaco viewer (ADR pre-dating this one; see "Frontend Monaco Setup" in CLAUDE.md) was extracted into a shared `ui/src/components/RawYamlModal.tsx`, and `api/maas_client.py` now renders a `raw_yaml` string per subscription/model via the same `yaml.safe_dump(..., sort_keys=False)` call `api/routes/config.py` already uses for run settings — so both views come from the same rendering path, not two independent YAML formatters. A model's `raw_yaml` combines its `MaaSModelRef` and (when internally served) the backing `LLMInferenceService` under `maasModelRef:`/`llmInferenceService:` keys, since debugging a serving issue usually needs both. **Caught during implementation, not anticipated up front**: initially importing `RawYamlModal` directly from `SubscriptionsTab`/`ModelsTab` pulled Monaco into the main JS bundle (confirmed via `npm run build`: main bundle jumped from ~390KB to ~3.1MB) because those tabs are reached eagerly from `App.tsx`, unlike `RunSettingsModal`, which was already behind `RunDetail.tsx`'s own `React.lazy` boundary. Fixed by giving each MaaS tab its own `React.lazy`/`Suspense` boundary around `RawYamlModal`, mirroring `RunDetail.tsx`'s existing pattern — any future direct (non-lazy) import of `RawYamlModal` will silently reintroduce this regression, so re-run `npm run build` and check for a standalone `RawYamlModal-*.js` chunk after touching either tab.

**Phase D (Rate Limiting, Networking, Platform Config) follows the same endpoint-per-resource-type pattern as Phase A, except Platform Config.** `list_rate_limit_policies()`/`list_limitador()` (Catalog D) and `list_gateways()`/`list_http_routes()` (Catalog F) each get their own `ResourceList`-returning function and route (`/api/maas/rate-limit-policies`, `/api/maas/limitador`, `/api/maas/gateways`, `/api/maas/http-routes`) rather than being folded into fewer, broader endpoints — each is backed by a different RBAC grant (`kuadrant.io`, `limitador.kuadrant.io`, `gateway.networking.k8s.io` respectively) and needs to degrade independently, exactly like Subscriptions/Models/Access already do. `list_platform()` (Catalog E) is the one exception: it returns a plain dict (`{tenants, data_science_cluster, odh_dashboard_config}`), each key with its own `available`/`reason`, rather than three separate endpoints — these three read as one settings page to a viewer, not three lists of similar objects, so a single `/api/maas/platform` call (still with per-section availability inline) matches how the Platform Config tab actually presents them.

**Deliberately excluded from Phase D**: Authorino `AuthConfig` (see Catalog D — hash-named, not filterable to MaaS-relevant ones, would be noise). Documented as a known gap in `docs/architecture/maas-domain-reference.md` rather than half-built.

**Models gained several more fields, all nullable-as-"unknown" rather than defaulting to a confirmed answer.** `has_auth_policy` (cross-referencing live `MaaSAuthPolicy.spec.modelRefs[]`, surfacing the community guide's governance-pairing rule — see Catalog B), `gateway_access_label` (reading the model's namespace via a new `CoreV1Api().read_namespace()` call, cached per-namespace within one `list_models()` call since several models commonly share a namespace), and each external provider's `credential_secret_label_ok` (below) all use `bool | None`, where `None` means the underlying read failed (RBAC/network) rather than "confirmed false." Collapsing that distinction would let a permissions gap in MaaS:PAL itself masquerade as a real misconfiguration in the cluster it's inspecting — the one failure mode every other part of this ADR's graceful-degradation design already treats as unacceptable.

**`has_auth_policy` grew a companion `auth_policies[]` list so the matching policy is one click away, not just a boolean.** `list_models()` now calls `list_auth_policies()` (same reuse as `list_subscriptions()`) instead of a raw `_list()` on `maasauthpolicies`, and indexes the shaped results by `(namespace, name)` so each model resolves the full set of `MaaSAuthPolicy` objects that actually cover it — `{name, namespace, display_name, ready, raw_yaml}` each. `ModelsTab.tsx`'s auth-policy column now renders each as a status label (green if `Ready`, grey otherwise) followed by an explicit `Button variant="link"` reading "View YAML" — not a clickable label on its own, which was tried first and immediately flagged live: every other status label in that table (gateway-access, hosting, credential-secret) is non-interactive, so a clickable one was visually indistinguishable and undiscoverable. The `YamlTarget`/`onSelect` plumbing (`ModelsTab.tsx`'s own "View YAML" button was generalized to share one `yamlTarget` state instead of a model-only `yamlModel` one) is unchanged — only the trigger element changed from the label itself to an adjacent link, matching how every other "view this CR's YAML" action in the MaaS Setup tabs (Subscriptions' row action, Access Control's group-name action) is already a visible link rather than an implicitly-clickable badge. `has_auth_policy` itself is unchanged (`len(auth_policies) > 0`, `None` only when the underlying `maasauthpolicies` read failed) — `auth_policies` is additive, not a replacement. **Note**: `AccessControlTab.tsx`'s `SubscriptionChips`/`AuthPolicyChips` still use the older clickable-label pattern this replaced — same discoverability gap, not yet revisited.

**ExternalModel migrated to the RHOAI 3.5+ schema, with no 3.4 fallback.** The cluster this repo targets is upgrading to 3.5, so `list_models()` now queries `inference.opendatahub.io/v1alpha1`'s `externalmodels`/`externalproviders` (split CRDs) instead of the 3.4-era single `maas.opendatahub.io/v1alpha1` `ExternalModel`. Deliberately not dual-checked the way `list_platform()`'s DataScienceCluster read is — that field-path check was cheap (two `.get()` calls on an object already fetched); supporting both `ExternalModel` shapes would mean querying two different API groups and merging two different result shapes for a resource with zero live instances to verify either against. If a 3.4 cluster's external-model support is needed later, treat it as a new, separately-verified addition rather than assuming the old code path still works — the schemas aren't drop-in compatible (single CRD vs. two, different field names throughout).

**Credential Secret check reuses the exact `_namespace_has_gateway_access_label` pattern**, but for Secrets: `_secret_has_label()` calls `CoreV1Api().read_namespaced_secret(name, namespace)` — `get` only, one specific already-known name (from the `ExternalProvider`'s own `spec.auth.secretRef`), never `list`/enumerate every Secret in a namespace, and only ever inspects `.metadata.labels` — `.data`/`.stringData` is never touched or logged. `deploy/rbac-maas-readonly.yaml` grants exactly `get` on `secrets`, nothing broader, specifically so this can't accidentally grow into something that reads credential contents.

**Access Simulator (Catalog item I) needed a new flat auth-policy list, which also let `list_access()` stop duplicating its own shaping.** `list_auth_policies()` was extracted from what used to be inline logic inside `list_access()`, shaped to mirror `list_subscriptions()` (`owner.{groups,users}`, per-model `model_refs[]`) specifically so the two lists compare model-by-model the same way. `list_access()` now calls it and adapts the shape locally rather than re-deriving it — a refactor with no behavior change (covered by the existing `list_access()` test suite, unmodified). `AccessSimulatorTab.tsx` itself is pure client-side derivation (`getMaasModels()` + `getMaasSubscriptions()` + the new `getMaasAuthPolicies()`) — no backend endpoint computes the resolution; for each model, the admin's candidate set is intersected against each subscription's/policy's `owner.{groups,users}` (matching either — a subscription/policy can name a user directly, not just via a group), the highest-`priority` matching subscription wins the quota question, and "reachable" requires a matching auth policy too. This was always designed to work this way (see Catalog item I's original note); it just hadn't been built yet.

**Candidate input is a typeahead-multi chip select, not a plain comma-separated text field.** `CandidateTypeahead` (inside `AccessSimulatorTab.tsx`) uses PatternFly's composable `Select`/`MenuToggle`/`TextInputGroup` pattern (not the deprecated `SelectVariant.typeaheadMulti` string-prop API) so it stays on the currently-supported PatternFly 5 API. Suggestions are every group/user name already referenced by some subscription's or auth policy's `owner` — not every OpenShift `Group` on the cluster — since an unreferenced group couldn't change any resolution result anyway and would just be typeahead noise; no new backend fetch was needed; the values were already in `subscriptions`/`authPolicies`, just not yet deduplicated into a suggestion list. Typing a value that matches nothing is still accepted (Enter, or a trailing comma, commits it as a chip) — the whole feature is for testing hypothetical group/user sets, including ones that don't exist yet. One import wrinkle: `@patternfly/react-icons`' icons are normally deep-imported from `dist/esm/...`, but that path isn't transformed by this repo's Jest config (no other component here had pulled in an icon before this one) — imported from `dist/js/...` (the package's own CJS build) instead, which Jest runs natively and Vite still bundles fine; if a future icon import here starts erroring the same way in Jest, use the same `dist/js/` path rather than adding a Jest transformIgnorePatterns override.

**Subscriptions gained per-model model-ref/auth-policy visibility, to make a missing or broken cross-reference obvious without leaving the tab.** A `MaaSSubscription` doesn't create the `MaaSModelRef` or `MaaSAuthPolicy` it depends on **at the CRD/controller level** — both remain independently-created objects it only references (see `docs/architecture/maas-domain-reference.md` Catalog item A for the verification: `harness/tasks/subscription.py` and `harness/tasks/access_policy.py` are two separate tasks, never both run by one scenario). **Correction** (see the domain-reference doc's own correction, and the new Authorization Policies tab below): the RHOAI Dashboard's own subscription-creation UI flow *does* auto-create a matching `MaaSAuthPolicy` as a one-time convenience — verified live, no `ownerReferences`/`labels` tie the two together, so it's not a K8s-native relationship and direct K8s API creation (this harness included) doesn't get it for free. Since nothing enforces that both actually exist and cover the subscription's owners, `list_subscriptions()` now resolves each `spec.modelRefs[]` entry against a fresh `maasmodelrefs` list (display name, `model_exists`, `model_ready` — `model_exists: false` is a genuine dangling reference, not a read failure) and against `list_auth_policies()` (`has_auth_policy`, matched the same way `AccessSimulatorTab.tsx`'s `resolveAccess()` does: any overlap between the subscription's and the policy's `owner.{groups,users}`, plus the same model). All three fields are `bool | None`, same convention as everywhere else in this ADR — `None` only when the cross-referenced CRD itself couldn't be read. `SubscriptionsTab.tsx`'s model-ref column now shows the resolved display name plus a `ModelRefBadge` (dangling/not-ready) and the same `AuthPolicyBadge` styling `ModelsTab.tsx` already uses, so a broken subscription is visible on sight rather than requiring a cross-check against the Models or Access Control tab. The field itself was named `model_refs` (both on `MaaSSubscription` and `MaaSAuthPolicy`, in both `api/maas_client.py` and `ui/src/api/client.ts`), not `models` — entries here are just `{name, namespace}`-shaped pointers into `spec.modelRefs[]` (enriched for display, in the subscription's case), not full model records the way `list_models()`/`MaasModel` are; `MaasModelSubscriptionRef`/`MaasAccessSubscriptionRef` already established the "-Ref" naming convention in `client.ts` for exactly this kind of thinner, reference-only shape.

**`has_auth_policy` is attached to each model ref, not to the subscription as a whole, because that's the actual granularity of the thing being checked.** A `MaaSAuthPolicy` covers a `(subjects, modelRefs)` pair, and its own `spec.modelRefs[]` can be a strict subset of a subscription's — so a subscription spanning two models can easily have gateway access for one and not the other under the exact same owners. Rolling this up to a single subscription-level badge would either overstate coverage (any match marked "OK") or understate it (any gap marked "missing"), and either way would hide exactly the information a debugging admin needs — which model is actually the problem. Per-model-ref is also what makes it a direct, literal answer to "is this model, from this subscription, actually reachable" rather than a derived summary the admin has to reinterpret.

**New "Authorization Policies" tab (between Models and Access Control), listing every `MaaSAuthPolicy` CR directly — the same CR-fidelity principle the Subscriptions tab already follows for `MaaSSubscription`.** Prompted by the correction above: since a `MaaSAuthPolicy` is a first-class, independently-created object (not merely derived from a subscription), it deserves the same direct listing Subscriptions gets, not just the Access Control tab's per-group cross-reference view (which stays unchanged and serves a different question — "what does this group have" vs. "what does this policy grant"). `list_auth_policies()` gained the same enrichment `list_subscriptions()` already had: `description`/`phase` (previously only `display_name` was captured), and each `model_refs[]` entry resolved against the live `maasmodelrefs` catalog (`display_name`, `model_exists`, `model_ready` — `bool | None`, same convention throughout). The modelref-lookup-building logic (`{(namespace, name): {display_name, ready}}` from a `maasmodelrefs` list) was extracted into a shared `_modelref_lookup()` helper used by both functions rather than duplicated a second time. `AuthorizationPoliciesTab.tsx` mirrors `SubscriptionsTab.tsx`'s layout (name/description/phase, target model(s) with `ModelRefBadge`, `OwnerChips`, View YAML) minus the rate-limit column, since auth policies carry no quota.

**Models' "View YAML" stopped combining unrelated CRs into one synthetic multi-key document.** `list_models()` previously built `raw_yaml` as `{"maasModelRef": cr, "llmInferenceService": llm_isvc}` (and `{"externalModel": cr, "externalProviders": [...]}` for external models) — two real, distinct Kubernetes objects concatenated under one YAML blob behind a single button, which reads nothing like a real `oc get -o yaml` and was reasonably flagged as looking like a bug. `raw_yaml` is now always exactly one object's own YAML (`MaaSModelRef` or `ExternalModel`); a new `serving_raw_yaml: str | None` carries the `LLMInferenceService`'s own YAML alone when resolved, and each `external_providers[]` entry gained its own `raw_yaml: str | None` for its resolved `ExternalProvider` CR. `ModelsTab.tsx` now shows a second "View Deployment YAML" link next to the primary one (internal models only, when `serving_raw_yaml` is present) and a "View YAML" link inline with each external provider's own info block — the same "action lives next to the specific thing it opens" principle just established for the auth-policy fix, applied consistently rather than left inconsistent between the two spots that had the same underlying issue.

## Consequences

**Positive:**
- Genuinely richer data than the REST API alone can provide (priority, group/user ownership, per-model quotas, live reconciliation status), sourced from the same CRDs RHOAI's own MaaS controller already treats as the source of truth.
- Fails soft everywhere: no RBAC applied, an unsupported MaaS version, or a cluster without MaaS at all all resolve to a clear per-section "unavailable" state rather than a crash or an opaque 500.
- No changes to any existing harness/runner code path — this is purely additive, read-only, and lives entirely in `api/`.

**Negative:**
- A new `ClusterRole`/`ClusterRoleBinding` must be applied for this feature to show anything at all — a fresh MaaS:PAL deployment without it will show every MaaS Setup section as unavailable until an admin applies `deploy/rbac-maas-readonly.yaml` (now included in the root `kustomization.yaml`).
- `list_models()` issues one `LLMInferenceService` `get` per internally-served model in addition to the two list calls — acceptable at the scale this tool targets (a handful of test models), but not designed to scale to hundreds of models without adding caching.
- `ExternalModel`'s schema is RHOAI-version-dependent (3.4 vs. 3.5+ use entirely different API groups — see the domain reference) and `api/maas_client.py` only queries the 3.5+ group/version, by design (the research cluster is upgrading to 3.5, and the two schemas aren't similar enough to cheaply dual-check the way `list_platform()`'s DataScienceCluster field path is). A 3.4 cluster's external models will silently not appear rather than error, since the query for the 3.5+ group/version just returns nothing on such a cluster. Neither the 3.5+ `ExternalModel`/`ExternalProvider` shape nor the `_secret_has_label` credential check have been verified against a live instance — written from the community guide's documented schema only.
- Access Control's all-or-nothing availability means a partial RBAC grant (e.g. subscriptions readable, auth policies not) shows nothing useful for that tab even though half the data exists — an accepted trade-off since a half-comparison could actively mislead an admin about which model coverage is actually missing.
- `list_models()` now also does one `CoreV1Api().read_namespace()` per unique model namespace, one `_list()` for `maasauthpolicies`, one `_list()` for `externalproviders`, and one `CoreV1Api().read_namespaced_secret()` per external provider with a credential ref (all cached/scoped within a single call where repetition is possible) — several more RBAC-gated read paths on top of the original two, all optional in the sense that failure degrades that field to `None` rather than the whole endpoint, but still more that can partially fail on a given cluster.
- The new `secrets` `get` grant in `deploy/rbac-maas-readonly.yaml`, despite being scoped as tightly as RBAC allows (verb-limited to `get`, no `list`/`watch`), is still the most sensitive permission this feature has ever requested — worth specifically re-reviewing if this ADR's RBAC list is ever audited, even though the code path never reads Secret `data`.

**Update (2026-10-05):** the page is now called **MaaS overview** (`/maaspal/overview`, sidebar entry "MaaS overview"; the old `/maaspal/setup` path redirects). "Setup" read as if the page configured MaaS; it only ever reads it.

**Neutral:**
- Introduces `api/maas_client.py` as a new, independent module rather than extending `api/k8s.py` — the two share no state and are called from different route groups.
